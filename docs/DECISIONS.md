# Decisions and history

Why things are the way they are. `CLAUDE.md` covers commands and architecture; this file covers the reasoning, the dead ends, and what's still open. Add to it when you make a decision a future contributor would otherwise have to rediscover.

## Product

- **The brief:** a game very like Omega Race (1981), but the force fields (the outer boundary and the central score box) change shape: rectangle, circle, cross and so on, with at least one level where they morph during play.
- **Name: "Omega Shift", not "Omega Race".** Omega Race is an existing arcade title, so the game, the repo (`omega-shift`) and the public URL use a distinct name. The local folder is still called `OmegaRace`, which is fine.
- **Gameplay follows the original:** rotate/thrust/fire ship with momentum; droids circle the arena and are promoted to command ships (shoot, lay photon mines), which become death ships (chase, lay vapor mines). Walls bounce the ship, and the side you hit flashes.
- **v1 scope:** the core game plus five shape levels (four more were added later: BAR, PILLAR, STAR, MALTESE; see below). Deliberately deferred: sound (added later; see below), a high-score table, an attract mode, and touch controls (the game is keyboard-only, so it doesn't work on phones).
- **Starfield background** (`src/render/stars.ts`, tuning in `STARS` in `src/config.ts`). The first version (160 dim stars, alpha 0.25–0.55, gentle flicker) was "a bit too muted", so the user asked for all four of: colour and twinkle, parallax drift, shooting stars, and reactions to the game.
  - **Stars:** 250, about 70% tinted (cyan, magenta, amber, violet or white; the rest pale blue-grey). Base alpha 0.45–0.8; 48% 1 px, 40% 2 px, 12% 3 px. (The agent's first tuning, half tinted with alpha from 0.35 and 60% at 1 px, still looked muted in real Chrome screenshots at 1:1, so it was pushed a notch.) The flicker is faster and deeper (1.5–5 rad/s, depth 0.3), with a twinkle swell (+0.45, sin⁸). About 10% are "sparklers" (2 px, tinted, base ≥ 0.7) that grow a four-point cross, up to 5 px, as they twinkle.
  - **Drift:** three layers at 4, 9 and 18 px/s. The heading turns slowly, as start + 0.012·t + 0.8·sin(0.045·t). Layer offsets wrap at 1024×768 (prev is shifted by the same amount, so the lerp by `alpha` never jumps), and stars are drawn at the interpolated offset and time.
  - **Shooting stars:** one every 4–10 s (the gap is drawn from the seeded RNG), tinted, 650–950 px/s for 0.75 s, with a 90–150 px fading tail.
  - **Reactions:** `enemyKilled`/`shipKilled` start a flare ring (520 px/s out to 420 px). Each star brightens when the ring reaches it (+0.55 enemy, +0.8 ship, times 1 − d/420) and decays with τ 0.55 s. A tinted star lifted by more than 0.2 grows a pixel and a small cross, which is what makes the ring readable on a sparse sky. `hyperspace` pulls stars within 280 px towards the landing spot and trails a streak for 0.4 s. `shipKilled` also flashes every star (+0.5, τ 0.25 s).
  - **No full-screen wash on ship death:** a 2048×1536 translucent fill costs more than the whole starfield on a software rasteriser.
  - **Readability:** nothing is drawn above alpha 0.85. White and pale stars of 2 px or more are capped at 0.55 and never grow, so no star reads as a bullet (a 2 px white dot with a glow). Alpha buckets round *down* (20 levels), so the caps hold after quantisation.
  - **Cost:** `fillRect` only, no `shadowBlur`, streaks drawn as at most 6 axis-aligned dashes (a staircase), batched into 6 colours × 20 alpha buckets. Per frame: calm, about 265 rects, 76 alpha changes and 0.035–0.045 ms of JS. Busy (four flares, a warp, a shooting star and the flash), about 770–790 rects and 0.08–0.10 ms of JS. The first warp version drew 1 px dots and issued about 2,400 rects in the busy case, which is why streaks are dashes now. Measured afterwards in headless Chrome (software raster, 2048×1536, 300 renders): the stars add 0.07 ms calm and 0.20 ms busy, inside the 0.3 ms budget.
  - **Deterministic for a seed, apart from time.** It runs on the fixed step, not wall-clock time, so it freezes while paused.
  - **Tests** (`tests/stars.test.ts`) cover determinism, the mix, wrapping, interpolation, alpha bounds through every reaction, the flare decaying back to base, the ring order (near stars before far) and the shooting-star rate.

## Technology

- **TypeScript + HTML canvas + Vite, no game engine.** The folder started as an empty IntelliJ Kotlin/Gradle/JDK 17 project. The user chose a browser stack over Kotlin + LibGDX, and the IntelliJ Gradle settings were removed. Canvas is enough for vector graphics, and a static bundle is trivial to host.
- **Fixed 120 Hz physics, rendering once per animation frame.** Together with the collision snap-back (below), a fixed step is enough to stop fast bullets tunnelling through walls, without swept collision.
- **Fixed 1024×768 logical world, letterboxed.** Level shapes are written in those coordinates.

## Force-field design

- **Fields are polar radius arrays** (star-shaped around the centre, sampled at N fixed angles). This was chosen over vertex-matched polygons because it makes three things trivial: morphing between *any* two shapes (just lerp the radii), an enemy track for every shape (the midline), and a corridor-safety guarantee (checking the keyframes is enough, because blends are linear). The cost is that shapes must be star-shaped around the centre, so no spirals or C-shapes.
- **N = 720, not 256.** At 256 samples, a rectangle's corner falls between two samples and is visibly cut off (a chamfer of roughly 15 px). 720 reduces it to about 5 px. `tests/stress.test.ts` passed at both values; re-run it if N changes.
- **Collision resolves the deepest contact first, and iterates.** The first version resolved edges in window order, so a neighbouring edge's shared vertex could win with a diagonal normal. Bounces off flat walls came out wrong, and the snap-back didn't hold. Resolving the true closest point first, up to three times, fixed this and still handles corners that touch two edges.
- **Bounces are relative to the wall's velocity.** That's what lets a morphing wall shove the ship instead of passing through it.
- **Wall flash lights the whole straight side** (as in the original), or a short arc on curves. The "straight" threshold is tied to `DTHETA` on purpose. With a fixed threshold, raising N made a circle's per-edge turn fall below the threshold, and a single hit lit half the ring.

- **Chambers come from the inner field overlapping the outer one**, not from a new kind of wall. Wherever the inner radius exceeds the outer, the corridor is closed; the open stretches between are chambers. This keeps everything a pair of polar arrays. The Maltese cross's arms have radial sides and a hub (r 40) smaller than the score circle (r 90), so each arm is sealed off.
- **Chambered keyframes must have radial (step) dividing walls, and can't be part of a morph.** Validation then stays per-sample: every sample is either open by `minGap` or closed, and each chamber is at least `minGap` wide along the track. Two continuous shapes that cross would leave arbitrarily narrow wedges, and blending into or out of a chamber pinches corridors shut, so the in-play morph guarantee wouldn't hold. Between-level transitions do pinch; the only thing alive then is the ship, and `Game` jumps it clear if its corridor gets narrower than the ship.
- **Spinning and breathing levels (SPIN, VORTEX) are motion on top of the keyframes, not keyframe swaps.** The user wanted continuously changing levels that were different in kind from SHIFT. Blending a shape into a rotated copy of itself doesn't turn it (the midpoint is a different, lumpy shape), so `LevelDef.motion` spins each field (rad/s, and the fields can counter-rotate) and scales it by 1 + amplitude·sin(2πt/period). One shared sine, so opposite signs breathe in antiphase.
  - **Spin resamples the shape specs at the turned angle each step** (`sampleShapeInto`). Shifting the sampled array would round off the star's tips. Star and Maltese vertex lists are cached per spec (a `WeakMap`), which took a spinning level's arena step from 0.39 to 0.10 ms (a still level is 0.02 ms).
  - **Wall velocity stays the finite difference of the radii at fixed angles.** For a rigid rotation that's the correct normal speed of the wall (radial speed × cos of the wall's angle to the radius), which is all collision uses. There's no friction along the wall. The stress test passes on both levels.
  - **Validation for motion levels:** when the fields spin at different rates, every relative angle comes round, so the corridor is checked at every whole-sample relative shift, with the outer field at its smallest breath and the inner at its largest. The inner field must stay at least `minInnerRadius` at its smallest. Because gap and blends stay linear in the radii, keyframes that pass still guarantee every moment in between. Chambers and an outside score can't have motion.
  - **The outer field must stay on screen** (a new check for every level): inside the 1024×768 box, and for a spinning outer within the half-height (384) at its largest breath. That rules out spinning a wide rectangle; VORTEX's cross has 330 px arms so its corners (about 376 px) clear 384.
  - **Level order is now 11:** SPIN is 5 and VORTEX is 10 (the user's placement). SHIFT stays last as the title showcase, with its speed scale raised to 1.35. The debug keys `0` and `-` reach levels 10 and 11.
- **Snap-back moves a crossed body to the nearest boundary point, not along its ray.** Along the ray was fine for walls that only move radially, but a body that crosses a radial chamber wall would be snapped to the hub, inside the score circle, and ping-pong between the fields. The nearest-point search window is sized by the ray penetration, which bounds the true distance. `collideArena` retries once, then puts the body on the nearest open track point as a last resort.
- **`chamberAt` treats the interval between a closed and an open sample as the open side's.** That interval holds the (near-radial) dividing wall; looking only at the left sample misclassified bodies in front of it.
- **Score outside the arena:** the bar and pillar leave no room for an inner field, so these levels set `scoreAt`. Their inner field is a zero-radius circle (not drawn, and `polyRadiusAt` returns 0 for it rather than 0/0), and the score readout glides from the centre to a panel outside the outer field during the transition. The inner-radius check is skipped for them.
- **An "I" can't have right-angle serifs:** the underside of a serif isn't visible from the centre. The user chose a plain thin bar (PILLAR) over angled serifs.
- **Hyperspace (H):** on a chambered level it goes to the next chamber clockwise (predictable, so you can plan a route), landing on the chamber's safest stretch; on a connected level, a random track point, like arcade hyperspace. Both have a 1.5 s cooldown and 0.75 s of invulnerability on arrival, and stop the ship. Chosen by the user.
- **Enemies in chambers:** a wave's droids are shared between the chambers the ship isn't in, so the player has to hyperspace to reach them. Track-followers turn back at a chamber's end wall, and the droids in a chamber turn together as a formation (turning individually made them pass through each other). Hunters only chase or shoot at a ship in their own chamber.
- **Track-followers move at a constant speed along the track**, not a constant angular speed, which bunched enemies on thin shapes (the bar's track is long and flat far from the centre). Wave droids are spaced 50 px apart along the track for the same reason.

## Performance and frame pacing

The user saw jittery motion on a display of unknown refresh rate. Measured first, then fixed.

- **Measuring:** `?debug` + `F` shows the last 240 frame intervals, the refresh rate (median interval, snapped to a common rate), a histogram of sim steps per frame, and update/render ms (`src/render/perf.ts`, fed by `startLoop`'s per-frame callback). Render ms is CPU time to issue the canvas calls; GPU time doesn't show up there.
- **The benchmark** was a temporary page (deleted afterwards) that built scenes through `Game` and rendered each at 2048×1536 (dpr 2) 100–200 times in headless Chrome. Headless Chrome's GPU process crashes in the agent sandbox, so this ran with `--disable-gpu` (Skia software raster): the absolute numbers are CPU-raster costs and much higher than a GPU would give, but the relative costs are what mattered. `--virtual-time-budget` sometimes froze `performance.now()` (every timing came out 0), so it was run without it; `--dump-dom` never returned with the Vite client connected, so results were read from a `--screenshot`.
- **Before → after (ms per frame, software raster):** SHIFT mid-morph 7.2–7.4 → 1.7; MALTESE with 9 droids and 64 particles 8.5–8.7 → 2.8–3.6; CLASSIC, no flash 7.4–8.3 → 0.7; CLASSIC with three sides flashing 10.1–10.8 → 0.8–1.1; worst case, every edge of both fields lit at different brightnesses, 15.7–16.6 → 7.3–8.5. The run-to-run noise is about ±0.8 ms.
- **The simulation is not the bottleneck:** a step averages 0.011–0.016 ms on MALTESE and SHIFT (a minute of play with shooting), p99.9 ≤ 0.2 ms, max 0.2–0.4 ms (the timer's resolution is 0.1 ms). So the jitter is frame pacing, not slow frames, and GC churn in the step (`[...this.enemies]`, `filter`s, `trackPoint` objects) and re-blending a static arena every step were **left alone**: no measurable pause, and skipping the re-blend would save a few µs per step at the cost of a "has it settled" state that must still zero the wall velocity on the first static step.
- **Render interpolation (the jitter fix).** Without it each frame drew the state after a whole number of 120 Hz steps: at 60 Hz that's 2 per frame with 1s and 3s whenever rAF timing wobbles; at 120 Hz it's 0/2 alternations around the step boundary; at 144 Hz a 1,1,1,1,1,0 pattern. Each is visible judder. Now `startLoop` passes `alpha = acc / step` to render and everything is drawn between its previous and current positions (ship heading too; enemy spin and particle angle aren't interpolated, as they're too small to see). The stepping maths is a pure function, `advance()`, unit-tested in `tests/loop.test.ts`. Physics is untouched: the existing tests pass unchanged.
- **Glow: shadowBlur costs in proportion to the path's bounding box**, and a force field's box is most of the screen. Blur 10 on the two 720-point field paths was about 90% of a frame with no flash. Each field is now stroked three times wide and faint under the real stroke (`haloStroke` in `draw.ts`); side-by-side screenshots look nearly the same (the blur's falloff is a little smoother). `shadowBlur` stays on the sprites and HUD text, whose boxes are small.
- **Batching the flash edges only helps without blur.** The first attempt batched lit edges into one path per brightness level (16 levels) but kept blur 16: CLASSIC with three sides lit went from 10.8 to 14.9 ms and the all-lit case from 16 to 100 ms, because one blurred path spanning the arena costs far more than many tiny blurred segments. With the halo strokes instead of blur, batching is a clear win and is kept.
- **Canvas setup:** `alpha: false` (an opaque canvas, so the compositor needn't blend it with the page). Raster time is the same either way, as expected. `desynchronized: true` was **not** applied: it trades vsync'd presentation for latency and can tear, the opposite of what jittery pacing needs, and nothing measured called for it. The `evenodd` clip in `drawArena` is skipped when `arena.isRing` (the fields can't cross, so it clipped nothing): SHIFT went from ~2.0 to 1.7 ms.
- **Still to check on the real display:** with `F`, the refresh rate and the steps-per-frame histogram (steady 2s at 60 Hz, 1s at 120 Hz, mostly 1s with some 0s at 144 Hz are all fine now that motion is interpolated), and whether any red long frames line up with events such as a wave spawning.

## Explosions

- **The brief:** "more explosive, bigger, with more lines flying apart". Every explosion now goes through `Game.blast(kind, x, y, color)`, which calls `spawnBlast` (`src/entities/particles.ts`) with a preset from `EXPLOSION` in `config.ts`.
- **Presets scale with danger: mine < droid < command < death < tanker < ship**, plus a small cyan `hyper` swirl for hyperspace (`curl` turns each fragment's velocity, so they spiral). Fragments per blast (shards + sparks, plus one ring and one flash): mine 24, droid 46, command 64, death 94, ship 128, hyper 30 (it was 8 / 16 / 16 / 16 / 30 / 12). Shards are 6–24 px (it was 3–9). Photon and vapor mines both use `mine`. `tests/particles.test.ts` checks the ordering.
- **Second pass: "bigger, with more debris flying around".** Every enemy and ship preset (not the smart bomb or hyperspace) got 1.8× the shards and sparks, 1.3× the launch speed and line length (sparks 1.25×), 1.25× the life, 0.8× the drag (so debris flies about 1.6× as far), 1.35× the ring and 1.25× the flash. Fragments per blast now: mine 44, droid 83, command 115, death 169, tanker 201, ship 231. Lines go up to 31 px, so the test's cap is 32. The 2000-particle cap is unchanged (eight ship deaths' worth). Not re-benchmarked: by the measurements below, fragments cost roughly 1 ms per 400 on the software rasteriser, so the busy case (three death ships and a ship death) should rise by about 2 ms there. Checked with a headless screenshot.
- **Parts of a blast:** tumbling **shards**; **sparks**, short streaks along their velocity that shrink as they burn out (60% of a shard's life, drawn one cooling step hotter); an expanding **shockwave ring** that eases out and thins; and a brief **flash**, a white disc over a coloured bloom. Fragments start white-hot and cool to the blast's colour over their life (`hotShare`, then 4 steps, `coolStep`). The ship's blast cools to orange, since white-to-white would read as nothing.
- **High launch speed with heavy drag** (e.g. death: 400 px/s, drag 2.3) makes it read as a burst rather than a drift. A fragment travels at most speed/drag px. The first screenshots used the lower speeds and looked like a slow puff.
- **Drawn without shadowBlur, batched.** Fragments are bucketed by (palette, cooling step, 8 alpha levels, shard or spark), and each bucket is one path stroked twice: a single halo pass (+4 px, alpha 0.2), then the core. Fragments use butt caps. Measured at 2048×1536 on the software rasteriser (the benchmark from "Performance and frame pacing"): MALTESE with 9 droids and no particles took 3.75 ms. Adding three death-ship blasts plus a ship death (418 particles) cost 5.2–6.0 ms in total, depending on the blast's age. Each extra halo pass cost about 1 ms (two passes 6.75, three 8.3). Round caps cost about 0.7 ms more with two passes. Rings plus flashes cost about 0.5 ms. That worst case is rare, and a GPU raster is much cheaper.
- **Capped at 2000 live particles**, dropping the oldest first (`spawnBlast` splices the front). A ship death is never lost to a full buffer.
- **Interpolation:** every particle spawns with prev = current, so nothing streaks from the origin in its first frame.
- **Screen shake is render-only.** `Game.shake` is an amplitude set by blasts with `shake > 0` (death ship 6 px, ship 10 px, capped at 12), decaying as exp(−7t) in `update`. `Game.shakeOffset` turns it into a wobble from a few sines of `game.time`, returns zero while paused, and `main.ts` applies it as a translate on the whole frame. Nothing in the simulation moves, so collision, tests and replays can't be affected, and the frame is deterministic for a given time. Only the two big deaths shake it, because shaking on every droid would be noise. Set `EXPLOSION.shake.enabled` to false to turn it off.

## Bonuses

- **The brief:** enemy ships leave bonuses behind as they move; they must look obviously worth collecting; the player flies through them. Three kinds: an extra life (lives cap at 6), points, and a smart bomb that kills every enemy on screen when the player presses B.
- **Dropped by a timer, not on death.** Every 6–11 s of a wave, a random live droid, command ship or death ship drops one where it is, with at most 3 waiting. The more dangerous the ship, the better the odds of a life or a bomb (`BONUS.weights`), so the best bonuses are the riskiest to fetch.
- **They look like nothing else:** the only round, rainbow-cycling things in the game (enemies are angular and one colour each, and every hue is already taken by some enemy, so no single colour would do). A pulsing ring, a faint ring in the complementary hue, three orbiting sparks, a white glyph (a ship for a life, `$`, `B`), a pop-in with overshoot, a two-tone "bling" when dropped, and blinking for the last 3 of their 12 s. First drawn at radius 13, enemy-sized, then raised to 16 so they stand out.
- **Caps convert to points:** a life at 6 lives, or a bomb with 3 held, scores `BONUS.points` (5000) instead, so a bonus is never wasted. Score extra lives stop at 6 too.
- **The smart bomb kills everything, in every chamber, mines included** (tankers excepted, see Tankers) ("all of the enemies on the screen"), scores them as normal kills, and clears enemy shots. Its kills are flagged `bombed`, so the audio plays one huge crash instead of a pile of explosions; the starfield flares and flashes.
- **Leftover bonuses survive the wave clear.** They used to be destroyed when a wave cleared, so a smart bomb could cost you the bonuses you were flying at. Now they stay collectable through the level card (they're updated there too, and the morphing walls shove them, but collision keeps them inside the arena) and fizzle when the next wave spawns.
- **Tests** (`tests/bonus.test.ts`): drops happen, the weights hold, each kind's effect, both caps, the bomb clearing a wave and reaching every Maltese chamber, expiry, bonuses staying inside the spinning VORTEX walls, collection during the level card, and a new game resetting bombs and bonuses.

## Tankers

- **The brief:** the learning curve was too shallow; a level could be cleared in seconds by picking off the slow droids. The user suggested a "tanker": hard to kill, spawning other enemy ships at random.
- **Armour, not speed.** A tanker crawls the track at 32 px/s, clockwise against the droids, so it's easy to hit but takes `ENEMY.tankerHp` (12) × the level's speed scale hits (14 on SPIN, 16 on SHIFT, more on later cycles). It flashes white and clanks on each hit, and an arc around it shows the armour left.
- **It keeps launching until destroyed:** every 2.5–5 s (divided by the speed scale), 65% droids, 25% command ships, 10% death ships. Hunters over `maxHunters` come out as droids, and nothing comes out while 16 ships (`maxShips`) are alive, so a player who ignores it gets a full arena, not an unbounded one. Each hit also has a 20% chance of knocking a droid loose, so rushing it has a cost.
- **How many, by round (the user's rule):** none in rounds 1–4, one in rounds 5–8, two in every round after that, however many times the list has repeated (`tankersFor`, `ENEMY.tankerRounds`). It's by round, not a per-level count, so the second time round the list keeps two. The four still levels teach the controls first. (The first version gave each level its own count plus one per repeat.) On a connected level they start a quarter turn from the ship and the droids; on the Maltese cross, near the far end of a chamber the ship isn't in. A launched droid joins its chamber's formation direction.
- **Wave bookkeeping:** the wave clears when no ship (anything but a mine, `isShip`) is left, so the tanker must die. Launches add to `waveSize`, so the pulse's "wave thinning" still means something. For the danger pulse a tanker counts as a command ship: it doesn't shoot, but it brings hunters.
- **Rewards:** 5000 points and a guaranteed bonus (40% life, 40% bomb), dropped even past `BONUS.maxLive`. It isn't a timed bonus dropper.
- **A smart bomb can't destroy one** (the user's rule): it does the damage of `ENEMY.tankerBombHits` (4) hits and always leaves at least one, so a bomb clears the tanker's escorts but never the wave. The first version let a bomb destroy it like everything else.
- **Not yet playtested.** The hit count, launch rate and weights are first guesses, like the rest of `ENEMY`.

## Welcome text

- **The brief:** text that appears over the title screen once it has sat waiting for a few seconds, in a vector font, telling the story (pilots in training, as in the original Omega Race) and explaining the enemy types.
- **The story is our own wording**, in the spirit of the original's premise (cadets trained against robot droid ships in a force-field arena), not a quotation, and it adds the arena that now shifts shape.
- **Two pages over the title**, not a separate screen: `YOUR MISSION`, then `KNOW YOUR ENEMY` (each ship's icon, name, points and a one-line description, plus mines and bonuses). Points come from `SCORE`, so they can't drift. 5 s untouched, then 16 s per page, typing at 80 characters/s, fading over 0.5 s, then 6 s of the plain title before it starts again. Any key or click resets the wait. The panel sits between the title and "PRESS ENTER", so both stay readable.
- **Our own stroke font** instead of a font file: the project has no assets or dependencies, and polylines on a 4×6 grid are exactly what vector arcade lettering was. Zero is slashed so it isn't read as O. The whole page is added to one path per string and drawn with `haloStroke` (no `shadowBlur`, since a page-sized blurred path is expensive; see Performance).
- **Sprites respect the caller's `globalAlpha`** (`drawEnemy`, `drawBonuses`), so the icons fade with the page. They used to reset it to 1.
- **Checked in headless Chrome** with a temporary page (since deleted) that renders the title with each page fully typed.
- **Title screen only.** The game-over screen still waits for Enter without it.

## Sound

- **The brief:** 80s-style sound; a sound whenever anything hits a force field; each enemy distinctive, more urgent the more dangerous it is. The user chose both a background pulse set by danger and per-action one-shots, with M toggling mute (remembered).
- **`Game` emits events instead of calling audio.** `Game` must stay free of DOM and browser APIs so tests can drive it headlessly; a `GameEvent` list keeps it that way and lets tests assert which sounds would play (`tests/sound.test.ts`). `main.ts` drains the list once per frame, after the frame's physics steps. The list is capped at 256 so a caller that never drains it (a test) doesn't grow it forever.
- **Field hits come from `collideArena`, tagged by the caller.** Collision already decides when a hit is hard enough to flash (`ARENA.flashImpact`), so "makes a sound" means exactly "flashes". The body classes pass a `source`; the stress test and other callers that pass none record nothing. Mines resting against a morphing wall get shoved every step, which is why hits are throttled.
- **Field-hit throttle: one per 40 ms per source** (`SOUND.hitThrottle`). At 120 Hz a body pinned by a moving wall, or a burst of shots, would otherwise stack dozens of voices and clip. Per source, so a shot hitting the wall doesn't swallow the ship's own bump.
- **Synthesised with Web Audio, no samples:** the project has no runtime dependencies and no asset pipeline, and raw square/saw/triangle oscillators plus white noise with fast envelopes and exponential sweeps *are* the 80s arcade sound. Every sound is a data "patch" (a list of layers) in `SOUND` in `config.ts`, so tuning by ear means editing numbers, not code. A compressor on the master bus (threshold -10 dB, ratio 6) stops explosions over the siren from clipping.
- **The second pass: "more 1980s, kind of annoying and quite drony, the kind of thing that catches your attention in a pub."** The first pass was tasteful and quiet; this one is deliberately raw and always-on. Everything below is from that pass.
- **A drone bed under everything** (`SOUND.drone`, `droneVoice`): square waves at 55 and 55.7 Hz, which beat at 0.7 Hz, through a resonant lowpass (Q 7) that a 0.06 Hz sine LFO sweeps between about 150 and 810 Hz. It is the always-on cabinet hum of Omega Race and Tempest. It plays during the wave *and* the level cards, and fades out (0.8 s) on pause, the title and game over. The bed is chosen by `ambientDanger` (`bed: 'play' | 'title' | 'off'`).
- **Danger levels: none < droid < command < death**, from the most dangerous enemy alive (mines don't count). Droid: slow low throb (62 Hz square, 1.2 Hz LFO). Command: faster, higher two-note warble (190 Hz, 2.5 Hz). Death: frantic rising sawtooth siren (650 Hz, 5.2 Hz). Each is a continuously running oscillator with one LFO on pitch and volume, and they crossfade over 0.3 s. The pulse only plays in `playing` and not paused.
- **The pulse gets louder, higher and faster as danger rises.** The first pass had the raw level *fall* with danger (droid 0.14, command 0.07, death 0.04 at the output). Now `gain` rises 0.18 < 0.24 < 0.32 (death has no lowpass at all), alongside pitch and LFO rate. `pulseSettings(danger, remaining)` in `engine.ts` is the pure function the engine uses, and the tests check it is monotone in danger.
- **The pulse also speeds up as the wave thins out**, like the Asteroids heartbeat. `ambientDanger` returns `remaining`, the fraction of the wave's droids, command and death ships still alive. The wave size is worked out the same way as in `Game.spawnWave` (`def.droids + 2 × cycle`), so keep the two in step. With the last ship left, the LFO rate doubles (`pulseUrgency.tempo: 1`) and the gain is 30% up (`pulseUrgency.gain: 0.3`). These are small enough that a lower danger with one ship left never outdoes a higher danger with a full wave, and a test checks that too. `main.ts` didn't change: `ambientDanger(game)` now returns an `Ambient` object (`danger`, `remaining`, `bed`), which `updateAmbient` takes.
- **Bit-crush on the master bus:** half the bus (`crush.mix: 0.5`) goes through a `WaveShaper` whose curve rounds the signal to 6 bits (`crushCurve`, no oversampling, so it aliases like a cheap DAC), and is summed back with the dry half. It is parallel, not in series, because rounding alone gates out quiet tails (anything under half a step becomes silence).
- **Harsher one-shots:** raw square and sawtooth waves with almost no filtering (the first pass ran many sounds through bandpass or lowpass filters, which is why the hits measured so low), longer tails, and all gains up.
- **Field hits have to cut through the drone and the pulse.** They measured 7–20× below the droid pulse, because narrow bandpasses (Q 3–4) threw away most of the energy. Now they are raw squares and saws at gain 0.3–0.45, and `hitGainRange` is [0.6, 1] rather than [0.35, 1], so even the softest hit is at least 0.6 of its full level. By arithmetic (an unfiltered square peaks at its gain), the softest ship, enemy and mine hits come out a little above the droid pulse, and the softest shot hit a little below it. That meets the target of hits within 2–3× of the pulse's peak.
- **Explosions are sized by the blast:** a noise crash through a lowpass sweeping down, plus a falling square wave and, from the command ship up, a saw growl. Mine 0.1 s < droid 0.5 s < command 0.9 s < death 1.4 s < the player's ship 2.2 s, with the noise gain rising 0.15 → 0.7. They don't use the event positions (there is no panning).
- **Title attract jingle:** an A-minor square arpeggio over a saw bass, a rising whoop and a held stab, about 2.2 s long (`SOUND.attract`). It plays 1.5 s after the first key press unlocks audio, and then every 20 s while the title is showing. Its timing runs on the audio clock, and it only plays through `patch()`, so `M` silences it (it keeps its schedule while muted, so unmuting doesn't set off a burst). Browsers block audio until a key press or click, so it can't attract anyone before that first interaction.
- **The AudioContext is created on the first keydown or click** (browsers block audio until a gesture), and suspended while the tab is hidden, since the frame loop stops then and the pulse would otherwise drone on. Mute is saved in `localStorage` under `omegaShift.muted`, wrapped in try/catch (blocked storage just means it isn't remembered).
- **First pass: rendered in real Chrome, but not yet listened to.** The agent's sandbox couldn't run headless Chrome, so the unit tests use a fake AudioContext that rejects illegal scheduling (exponential ramps to 0, negative times). Afterwards every event, each pulse and the thrust were rendered through the real engine into Chrome's `OfflineAudioContext` (a temporary page, since deleted): all finite, no errors, nothing near clipping. Peaks: field hits 0.006–0.020, player and enemy one-shots 0.014–0.13, droid pulse 0.14, command 0.07, death 0.04, thrust 0.02. Note `play()` only schedules while the context is `running`, so an offline check has to stub `state` (and `resume`).
- **Second pass: rendered in real Chrome afterwards** (the sound agent's sandbox couldn't launch it; same offline method, `state`, `resume` and `suspend` stubbed). All finite, no errors. Measured peaks: pulse droid 0.11 → 0.15 with the wave nearly gone, command 0.15 → 0.18, death 0.15 → 0.19 (rising with danger and with the wave thinning, as intended). Drone alone 0.08; drone + droid pulse, the real play mix, 0.16. The agent's arithmetic had the hits at 0.09–0.23, but they measured 0.03–0.07, 2–5× under the play mix. So the hit gains were raised (ship 0.6, enemy and mine 0.75, shot 0.55) and now measure 0.06–0.11, within 1.5–2.7× of the play mix. Explosions: droid 0.08, command 0.18, death ship 0.23, player 0.33. Attract jingle 0.37 as a raw patch, before the master bus. An offline context's clock doesn't run until rendering, so the jingle's 1.5 s first delay never elapses there; render its patch directly.

## Testing

- **Unit tests** cover the shape maths, the morph timeline, level validation, and collision (flat walls, moving walls, the inside corners of the cross, snap-back).
- **`tests/stress.test.ts`** runs 200 fast bodies per level for 60 simulated seconds and asserts none escape the corridor or leave the chamber they started in. This is the main guard for any change to physics, shapes or N. With nine levels the suite takes about 17 s.
- **`tests/sound.test.ts`** checks which `GameEvent`s fire (field hits by source, promotions, enemy fire, kills), `dangerLevel` ordering, the ambient bed per state, the remaining-wave fraction, that the pulse's gain, pitch and rate rise with danger and its rate as the wave thins, and the bit-crush curve. It also runs the audio engine against a fake AudioContext, checking that every event starts at least one source, that ambient voices aren't rebuilt per frame, and that the attract jingle fires on schedule, only on the title and not while muted.
- **`tests/game.test.ts`** drives `Game` headlessly with a fake `Input`: five minutes of random play, plus a check that clearing a wave morphs the arena into the next level.
- **The long simulation tests have a 60 s timeout.** Each takes about 1.5 s on a laptop (the whole suite about 8 s), but they went over Vitest's 5 s default on GitHub's runners, which broke the first deploy.
- **The whole suite now has a 60 s timeout** (`testTimeout` in `vite.config.ts`), not just the tests marked as long. The bonuses deploy failed because the starfield's alpha test (0.9 s locally) took 5.2 s on the runner, which is about 5.5× slower. Marking long tests one by one kept missing new ones.
- **Visual checks** have been headless Chrome screenshots (`--headless=new --screenshot`), sometimes via a temporary preview page that renders every level; that page was deleted afterwards. The Claude in Chrome extension was declined, so don't suggest it.
- **README screenshots** (`docs/screenshots/`) were staged by a temporary page that drives the real `Game` into each scene (scripted flying, a forced kill, a hyperspace or smart bomb at a set moment) and draws it with the same calls as `main.ts`, captured at 1024×768 in headless Chrome over the DevTools protocol. Re-stage them the same way after visual changes.

## Deployment

- **Live site:** https://richard-i-anderson.github.io/omega-shift/. **Repo:** https://github.com/richard-i-anderson/omega-shift (public, because Pages on a free plan needs a public repo).
- **`.github/workflows/deploy.yml`** runs on every push to `main`: `npm ci` → `npm test` → `npm run build` → publish `dist/` to Pages. A failing test blocks the deploy. Pages is set to build type "workflow".
- **Vite `base: './'`** keeps asset paths relative, so the build works in the `/omega-shift/` subpath (and on any other static host).
- **Commits use the GitHub noreply address**, configured in this repo only, so the user's real emails stay out of public history. Don't change it.
- **Pushing:** the user's git credential helper is the macOS keychain, which may not have a GitHub login. Push with `git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push`, or ask the user to run `gh auth setup-git` once (it changes their global git config, so ask first). Pushing workflow files needs the gh token's `workflow` scope; it has been granted.
